# cubot_urdf — the shipped CuBot chain as a URDF

`cubot_shipped.urdf` is the 27-module chain in the **shipped hard configuration** from
`roll.html` / `CuBot/presets/shipped.json`, with the cube geometry taken from the printed CAD
(outer profile only). `cubot_shipped.xml` + `scene.xml` are the same chain as MuJoCo MJCF with a
free base and a floor. Everything is generated by `build_cubot_urdf.py` — edit that, not the outputs.

```
python3 build_cubot_urdf.py          # needs numpy + scipy  -> urdf, xml, scene, meshes/
python3 measure_cad_profile.py       # re-derives the chamfer + neck numbers from ~/Desktop/CuBot CAD
python3 -c "import mujoco; mujoco.MjModel.from_xml_path('scene.xml')"   # load check
python3 make_viewer.py               # bundles urdf + meshes into viewer.html — open it in any browser
python3 make_fold_viewer.py          # bundles urdf + meshes + ../cubot-v2/handoff paths into fold_viewer.html
```

`viewer.html` parses the URDF text at load, builds the chain from the joints it finds, decodes the STLs, and runs
checks (roll word read from the mounts, pitch/gap, axes, mass, mesh bounds, span, cumulative roll) — if the URDF is
wrong, the viewer shows it wrong. Click a module, drive its servo to detents or sweep it, toggle the ideal-cube ghost
to see what the chamfers and neck remove.

`fold_viewer.html` animates the seven handoff paths (`../cubot-v2/handoff/shapes/*/path.json`) on the same URDF chain:
pick a shape, play / scrub / step through the moves, or unfold back to the straight chain. `out` moves swing the tail side;
`in` moves hold the tail and swing the base side, so the base re-orients and T, N and lightning finish standing on edge,
exactly as `final_tracked` predicts. At load the page replays every path and checks each rest pose against the planner's
`cells_after` / `base_after` (the header shows the result). Rest poses are settled onto z = 0 like the planner does; the
settle is blended into the last 20 % of each move so scrubbing never jumps.

## Conventions (all confirmed 2026-09-19)

| | |
|---|---|
| Modules | 27, straight along **+X**, Z up, module 1 centre at the origin (scene lifts it 40 mm onto the floor) |
| Cube | 80 mm, cut by `x+y+z=0` (normal = ⟨111⟩ body diagonal). Still half = −x−y−z side (roll.html "inboard"); moving half = +x+y+z side ("outboard") |
| Chamfers | 45°, **8.00 mm** legs on the **six equatorial edges** (`\|x−y\|,\|y−z\|,\|z−x\| ≤ 72`). Apex corners sharp. Ridge where two chamfers meet is parallel to ⟨111⟩ at r111 = 58.788 mm (matches `CuBot/tools/build-solid.mjs`). Printed part measures 7.85 mm; 8.00 is the design value |
| Neck | Near the cut plane each half is turned down about the hinge axis. The measured outer profile (r_max per 1 mm of height on the hulls of Top.stl and Bottom_V12+Hub_Still, which mirror each other) is bounded by one cone `r ≤ 46.8 + 1.13·|t|` mm, revolved as a 12-gon. This is what lets a half swing at a 2.2 mm gap (un-necked ideal half sweeps 2.33 mm past its own face, this model 0.63 mm, printed part 0.06 mm) |
| Gap | **2.2 mm** face-to-face → centre pitch **82.2 mm**. A 50×50×2.2 mm spacer box (footprint of `CuBot_Spacer.stl`) is rigid on each moving half's +X face (26 of them) |
| Roll word | `12001300133101230333233210` — digit k: module k+1 mounted rolled `r·90°` **right-hand about +X** (+X toward module 27) relative to module k, i.e. `M_{k+1} = M_k · Rx^{r_k}` exactly as roll.html |
| Servo | `continuous`, axis `+(1,1,1)/√3` from still into moving, right-handed. q = 0 is the straight chain. Detents are 120° apart, travel −240..+240°: the controller enforces that, not the file. `<limit effort="5.8" velocity="1.2">` is informational (60 % STS3215-12V register through 4:1) |
| Mass | 250 g/module, 125 g per half, uniform density; inertia integrated exactly over the polytope. Spacers massless |
| Root | floating. The URDF root link `m01_still` is what a loader welds to the world; the MJCF adds `<freejoint>` |
| Units | metres, radians, kg. Mesh paths are relative to the URDF (`meshes/*.stl`, STL already in metres) |

Link/joint names: `mNN_still`, `mNN_moving`, `servoNN` (still→moving), `mountNN_MM` (fixed, moving NN → still MM).
Both `<visual>` and `<collision>` use the same convex mesh, so the chamfers and the neck are in the collision solid.

## What was verified

* Both half meshes: **43 vertices / 82 triangles**, convex (MuJoCo collides the hull directly), volume 247.2 cm³ (real Top.stl hull 240.1, ideal half-cube 256). Each half is one rigid link with one mesh; the moving half also carries the spacer box. Nothing else.
* The solids contain the real CAD hulls to within +0.111 mm (that is the 8.00 vs 7.85 mm chamfer choice; nothing else sticks out).
  The Hub_Still cone that protrudes past the cut plane sits ≥ 5.4 mm inside the moving half's neck at every height, for every angle.
* Inertia integrator checked against the analytic cube (mL²/6) and the ideal half-cube (COM at 13a/48, (2/3)ma² about the centre).
* MuJoCo 3.13 loads both files: 55 bodies, 27 servos, 6.750 kg, span 26 × 82.2 = 2137.2 mm, every module's world
  rotation equals the cumulative roll of roll.html, every servo axis = module frame · ⟨111⟩, zero non-floor contacts at q = 0.
* Physics (scene.xml, 2 ms steps, implicitfast): chain settles on the floor with zero drift, servos hold to 0.005°, modules 1 and 27
  reach ±120° detents under the position actuators, no non-floor penetration at any point, all states finite; 3–13× realtime on a laptop.
  Servo 13 stalls at −18° trying to lift 14 modules against the 5.8 N·m `forcerange` — set `EFFORT_NM` higher (or remove
  forcerange) if you want idealized servos for shape generation.
* Kinematic swing from the straight chain: every single-joint 0 → ±120° move is penetration-free; the 0 → ±240° routes
  pass through 160–200° where the two neighbouring modules hit each other (−14.6 mm) — that is the machine, not the model.

## Not modelled (by decision)

Pockets, bores, the bearing/hub internals, the pinion, wiring; anything inside the outer profile. The printed chamfer is
7.85 mm, the file uses the 8.00 mm design value.
